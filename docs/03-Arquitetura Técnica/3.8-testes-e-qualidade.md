# 3.8 Testes e Qualidade

## Objetivo

Este documento define as estratégias de teste e os critérios de qualidade utilizados no desenvolvimento do Arqio.

O objetivo é identificar erros, verificar as regras de negócio e garantir que as funcionalidades funcionem conforme os requisitos definidos.

Os testes serão implementados gradualmente, acompanhando o desenvolvimento de cada funcionalidade do MVP.

---

## Estratégia de Testes

O Arqio utilizará diferentes tipos de testes, conforme a necessidade de cada parte da aplicação.

### Testes Unitários

Os testes unitários verificarão funções e unidades específicas de código de maneira isolada.

Serão utilizados principalmente para testar:

- Regras de negócio;
- Validações de dados;
- Cálculos e transformações;
- Funções auxiliares;
- Verificações de permissões.

### Testes de Integração

Os testes de integração verificarão se diferentes partes do sistema funcionam corretamente em conjunto.

Serão utilizados para testar:

- Comunicação entre rotas, controllers e services;
- Integração entre o backend e o MongoDB;
- Autenticação nas rotas protegidas;
- Operações de criação, consulta e atualização de registros;
- Tratamento de erros durante as operações.

### Testes de Ponta a Ponta

Os testes de ponta a ponta, também chamados de testes E2E, verificarão fluxos completos da aplicação.

Esses testes poderão simular ações como:

- Cadastro e login de um usuário;
- Criação de uma empresa;
- Cadastro de um projeto;
- Consulta dos documentos de um projeto;
- Verificação de acesso conforme as permissões.

Os testes E2E serão introduzidos conforme as funcionalidades essenciais estiverem disponíveis.

---

## Ferramentas

As ferramentas definitivas serão escolhidas de acordo com a estrutura do projeto.

Para o backend desenvolvido com Node.js e TypeScript, poderão ser utilizadas ferramentas como:

- **Vitest ou Jest:** execução de testes automatizados;
- **Supertest:** testes de solicitações HTTP à API;
- **MongoDB de teste:** execução de testes que dependam do banco de dados.

A escolha das ferramentas deverá evitar complexidade desnecessária e manter compatibilidade com as tecnologias utilizadas.

---

## Testes de Autenticação

A autenticação será testada para verificar se somente usuários com credenciais válidas conseguem acessar as funcionalidades protegidas.

Os testes deverão verificar:

- Login com credenciais válidas;
- Rejeição de credenciais inválidas;
- Rejeição de tokens inválidos ou expirados;
- Bloqueio de rotas protegidas sem autenticação;
- Recuperação de senha, quando implementada;
- Proteção das informações sensíveis.

---

## Testes de Autorização

Os testes de autorização verificarão se cada usuário pode executar somente as operações permitidas para sua função.

Deverão ser verificados cenários como:

- Usuário autorizado acessando um projeto;
- Usuário sem permissão tentando alterar um projeto;
- Usuário sem vínculo tentando acessar uma empresa;
- Usuário tentando consultar documentos de outro projeto;
- Tentativa de acessar recursos de outra empresa por meio de identificadores conhecidos.

Os testes deverão confirmar que a segurança é aplicada no backend, independentemente do comportamento da interface.

---

## Testes de Integridade dos Dados

Os testes deverão verificar se os dados são armazenados e relacionados corretamente.

Serão avaliados:

- Unicidade do e-mail dos usuários;
- Integridade dos vínculos entre usuários e empresas;
- Associação correta entre empresas e projetos;
- Associação correta entre projetos e documentos;
- Validação dos campos obrigatórios;
- Tratamento de referências inexistentes;
- Preservação do histórico de versões dos documentos, quando implementado.

---

## Testes de Arquivos

As funcionalidades de armazenamento de arquivos deverão ser verificadas para garantir que os arquivos sejam enviados, identificados e acessados corretamente.

Os testes deverão considerar:

- Envio de formatos permitidos;
- Rejeição de formatos não aceitos;
- Rejeição de arquivos acima do limite definido;
- Acesso por usuários autorizados;
- Bloqueio de acesso por usuários não autorizados;
- Tratamento de falhas no armazenamento;
- Preservação das versões anteriores dos documentos.

---

## Tratamento de Erros

Os testes deverão verificar se a aplicação responde adequadamente a erros previsíveis e inesperados.

Serão avaliados:

- Dados inválidos;
- Recursos inexistentes;
- Falhas de autenticação;
- Falhas de autorização;
- Indisponibilidade do banco de dados;
- Falhas no armazenamento de arquivos;
- Erros inesperados no backend.

As respostas deverão utilizar códigos HTTP adequados e não deverão expor senhas, segredos ou detalhes internos desnecessários.

---

## Qualidade do Código

O desenvolvimento deverá seguir práticas que facilitem a leitura, a manutenção e a evolução do sistema.

Os critérios incluem:

- Utilização de TypeScript para reduzir erros relacionados aos tipos;
- Separação de responsabilidades entre as camadas;
- Nomes claros para funções, variáveis e arquivos;
- Validação dos dados recebidos pela API;
- Tratamento consistente de erros;
- Evitar duplicação desnecessária de código;
- Organização dos arquivos conforme a arquitetura definida;
- Registro das alterações no Git por meio de commits descritivos.

O uso de TypeScript não elimina a necessidade de validar dados recebidos externamente, pois informações enviadas por usuários e serviços podem estar incorretas.

---

## Critérios para Conclusão de uma Funcionalidade

Uma funcionalidade poderá ser considerada concluída quando:

- Atender aos requisitos definidos;
- Validar os dados necessários;
- Aplicar as permissões correspondentes;
- Tratar os principais cenários de erro;
- Persistir os dados corretamente, quando aplicável;
- Possuir testes compatíveis com sua complexidade e criticidade;
- Não comprometer funcionalidades existentes;
- Ter sido revisada e registrada no Git.

A quantidade e a profundidade dos testes deverão considerar os riscos da funcionalidade, priorizando autenticação, autorização e isolamento de dados.

---

## Execução dos Testes

Os testes serão executados durante o desenvolvimento e antes de alterações importantes.

Quando a estrutura do projeto estiver preparada, serão definidos comandos padronizados para executar os testes do backend e, posteriormente, do frontend.

Os testes automatizados deverão ser complementados por verificações manuais dos fluxos principais do MVP.

# 3.2 Fluxo da Aplicação

## Objetivo

Este documento descreve como as informações circulam dentro do Arqio, desde a interação do usuário com a interface até o processamento das solicitações pelo backend e o acesso ao banco de dados.

O objetivo é estabelecer um fluxo organizado, seguro e consistente para a comunicação entre as partes do sistema.

---

## Visão Geral do Fluxo

A aplicação será organizada em três partes principais:

- **Frontend:** interface utilizada pelos usuários para acessar as funcionalidades do Arqio.
- **Backend:** responsável por receber as solicitações, validar os dados, verificar permissões e executar as regras de negócio.
- **Banco de dados:** responsável por armazenar e consultar as informações da plataforma.

A comunicação entre o frontend e o backend ocorrerá por meio de uma API HTTP, utilizando dados no formato JSON sempre que apropriado.

---

## Fluxo de uma Solicitação

O fluxo padrão de uma solicitação será:

1. O usuário realiza uma ação na interface.
2. O frontend envia uma solicitação para a API.
3. O backend recebe a solicitação por uma rota.
4. Os middlewares executam as verificações necessárias, como autenticação e validação.
5. O controller recebe a solicitação e coordena seu processamento.
6. O service executa as regras de negócio.
7. O repository, quando utilizado, realiza a comunicação com o banco de dados.
8. O MongoDB retorna os dados solicitados ou confirma a operação.
9. O backend envia uma resposta para o frontend.
10. O frontend apresenta o resultado ao usuário.

Nem toda solicitação precisará executar todas essas etapas. Por exemplo, algumas operações poderão ser concluídas sem consultar o banco de dados.

---

## Responsabilidades de Cada Camada

### Frontend

O frontend será desenvolvido com React, TypeScript e Vite.

Suas responsabilidades serão:

- Exibir as páginas e os componentes da interface.
- Permitir a interação dos usuários com as funcionalidades.
- Coletar informações por meio de formulários.
- Enviar solicitações para a API.
- Apresentar os resultados recebidos.
- Exibir mensagens de erro e confirmação.

O frontend não será responsável por garantir a segurança das operações. As verificações de acesso deverão ocorrer no backend.

### Rotas e Middlewares

As rotas definirão os endereços da API e os métodos HTTP utilizados para acessar cada funcionalidade.

Os middlewares serão responsáveis por verificações que precisam ocorrer antes do processamento principal, como:

- Verificar o token de autenticação.
- Validar informações da solicitação, quando aplicável.
- Identificar o usuário autenticado.
- Aplicar verificações iniciais de segurança.

### Controllers

Os controllers receberão as solicitações encaminhadas pelas rotas e coordenarão a execução da operação.

Suas responsabilidades incluirão:

- Ler os parâmetros e os dados enviados.
- Acionar os services necessários.
- Definir o código de status HTTP da resposta.
- Retornar os dados ou as mensagens de erro apropriadas.

Os controllers deverão evitar concentrar regras de negócio complexas.

### Services

Os services conterão as regras de negócio da aplicação.

Suas responsabilidades incluirão:

- Verificar as condições necessárias para executar uma operação.
- Aplicar as regras funcionais do sistema.
- Verificar permissões específicas da operação.
- Coordenar operações que envolvam diferentes recursos.
- Acionar os repositories quando for necessário acessar os dados.

### Repositories

Os repositories serão responsáveis por organizar as operações de acesso ao banco de dados, quando essa camada for utilizada.

Suas responsabilidades incluirão:

- Consultar documentos armazenados.
- Criar novos registros.
- Atualizar informações.
- Excluir ou arquivar registros, conforme as regras definidas.

Essa separação ajuda a manter as regras de negócio independentes dos detalhes de acesso ao banco de dados.

### Banco de Dados

O MongoDB armazenará os dados persistentes do Arqio, incluindo usuários, empresas, projetos, documentos e demais informações definidas na modelagem.

O acesso ao banco de dados será realizado pelo backend, utilizando o Mongoose.

O frontend não se conectará diretamente ao MongoDB.

---

## Exemplo de Fluxo: Cadastro de um Projeto

Quando um usuário autorizado cadastrar um projeto, o fluxo será:

1. O usuário preenche o formulário de cadastro no frontend.
2. O frontend envia os dados do projeto para a API.
3. O backend identifica o usuário autenticado.
4. O sistema verifica se o usuário tem permissão para criar projetos naquela empresa.
5. Os dados recebidos são validados.
6. O service aplica as regras de negócio do cadastro.
7. O repository salva o projeto no MongoDB.
8. O backend retorna uma resposta de sucesso com os dados pertinentes.
9. O frontend informa que o cadastro foi concluído e atualiza a interface.

Se os dados forem inválidos ou o usuário não tiver autorização, a operação deverá ser interrompida e uma resposta apropriada deverá ser enviada.

## Comunicação entre Frontend e Backend

A comunicação utilizará os seguintes padrões:

- **Protocolo:** HTTP durante o desenvolvimento local e HTTPS em produção.
- **Formato dos dados:** JSON para solicitações e respostas que transportem dados estruturados.
- **Métodos HTTP:** utilizados conforme a operação solicitada.
- **Autenticação:** token JWT nas solicitações que exigirem usuário autenticado.
- **Tratamento de erros:** respostas com códigos HTTP e mensagens apropriadas.

Os métodos HTTP mais comuns serão:

| Método | Finalidade |
|---|---|
| `GET` | Consultar informações |
| `POST` | Criar registros ou executar operações |
| `PUT` | Substituir um recurso, quando necessário |
| `PATCH` | Atualizar parcialmente um recurso |
| `DELETE` | Excluir um recurso, quando permitido |

A escolha do método deverá refletir a finalidade da operação.

---

## Códigos de Resposta HTTP

A API utilizará códigos HTTP para indicar o resultado das solicitações.

| Código | Significado |
|---|---|
| `200` | Solicitação concluída com sucesso |
| `201` | Recurso criado com sucesso |
| `400` | Dados inválidos ou solicitação incorreta |
| `401` | Autenticação necessária ou inválida |
| `403` | Usuário sem permissão para executar a operação |
| `404` | Recurso não encontrado |
| `500` | Erro interno inesperado |

As respostas deverão manter um padrão consistente para facilitar o tratamento no frontend.

---

## Segurança do Fluxo

O backend deverá ser responsável por garantir a segurança das operações.

As seguintes regras deverão ser aplicadas:

- Verificar a identidade do usuário nas rotas protegidas.
- Validar os dados recebidos antes de processá-los.
- Verificar as permissões antes de permitir acesso ou alteração de recursos.
- Garantir o isolamento dos dados entre empresas.
- Evitar expor informações sensíveis nas respostas.
- Tratar erros sem revelar detalhes internos desnecessários.
- Utilizar HTTPS em produção.

O frontend poderá ocultar opções que o usuário não tem permissão para utilizar, mas essa medida será apenas uma melhoria da interface. A autorização efetiva deverá ocorrer no backend.

---

## Tratamento de Erros

Os erros deverão ser tratados de forma consistente em toda a aplicação.

O backend deverá retornar o código HTTP adequado e uma mensagem que ajude a identificar o problema sem expor informações internas.

O frontend deverá interpretar as respostas e apresentar mensagens compreensíveis ao usuário.

Erros inesperados deverão ser registrados de forma apropriada para facilitar a investigação e a manutenção do sistema.

---

## Princípios de Organização

O fluxo da aplicação deverá seguir estes princípios:

- Separação de responsabilidades entre as camadas.
- Validação de dados no backend.
- Verificação de autenticação e autorização antes de operações protegidas.
- Comunicação padronizada entre frontend e backend.
- Acesso ao banco de dados exclusivamente pelo backend.
- Tratamento consistente de erros.
- Organização que facilite testes, manutenção e evolução do sistema.

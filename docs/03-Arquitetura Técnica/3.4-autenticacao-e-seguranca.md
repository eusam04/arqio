# 3.4 Autenticação e Segurança

## Objetivo

Este documento define as estratégias de autenticação, autorização e proteção dos dados do Arqio.

O objetivo é garantir que cada usuário acesse somente os recursos para os quais possui permissão, protegendo as informações pessoais, empresariais e dos projetos.

---

## Autenticação

A autenticação será responsável por verificar a identidade do usuário que deseja acessar a plataforma.

O sistema utilizará autenticação por e-mail e senha.

### Fluxo de login

1. O usuário informa seu e-mail e sua senha.
2. O frontend envia as credenciais para o endpoint de login da API.
3. O backend procura a conta correspondente ao e-mail informado.
4. O sistema compara a senha recebida com o hash armazenado.
5. Se as credenciais forem válidas, o backend gera um token de autenticação.
6. O frontend utiliza o mecanismo de sessão definido para acessar as rotas protegidas.

Se as credenciais forem inválidas, a API deverá retornar uma resposta apropriada sem revelar se o e-mail ou a senha foi o dado incorreto.

---

## Proteção de Senhas

As senhas dos usuários nunca deverão ser armazenadas em texto puro.

O backend utilizará uma biblioteca apropriada para gerar e verificar hashes de senhas, como o bcrypt.

### Regras

- Armazenar somente o hash da senha.
- Nunca retornar hashes nas respostas da API.
- Nunca registrar senhas em logs.
- Verificar a senha informada durante o login utilizando a função de comparação da biblioteca.
- Exigir uma política de senha adequada à segurança da plataforma.

O hash será gerado no cadastro ou na alteração da senha e armazenado no campo `passwordHash` da coleção `users`.

---

## Autenticação com JWT

O Arqio utilizará JSON Web Tokens (JWT) para representar a autenticação nas solicitações protegidas da API.

Após um login válido, o backend emitirá um token com informações mínimas necessárias para identificar o usuário e controlar sua validade.

### Regras

- O token deverá possuir prazo de validade.
- O backend deverá verificar a assinatura e a validade do token.
- Tokens inválidos ou expirados não poderão autorizar operações.
- O token não deverá conter senhas ou outros dados secretos.
- As permissões atuais do usuário deverão ser verificadas no backend, e não presumidas apenas a partir do token.

### Armazenamento do token

A estratégia de armazenamento deverá priorizar a segurança contra roubo de sessão e ataques de scripts.

A implementação deverá avaliar o uso de cookies `HttpOnly`, `Secure` e `SameSite`, com proteção adequada contra ataques CSRF quando necessária.

Se outra estratégia de armazenamento for escolhida, os riscos de exposição do token deverão ser considerados. O token não deverá ser armazenado em locais acessíveis a scripts da página sem uma avaliação de segurança.

---

## Autorização

A autorização será responsável por determinar quais operações um usuário autenticado pode executar.

A autenticação confirma quem é o usuário. A autorização determina o que ele pode fazer.

As permissões serão verificadas de acordo com os vínculos do usuário com empresas e projetos.

### Permissões por empresa

O vínculo entre usuário e empresa, registrado em `companymemberships`, determinará sua função e seu nível de acesso dentro daquela organização.

Exemplos de funções:

- Administrador da empresa;
- Arquiteto;
- Engenheiro;
- Encarregado de obra;
- Cliente;
- Outros profissionais autorizados.

As funções definitivas e suas permissões deverão seguir as regras funcionais documentadas para o produto.

### Permissões por projeto

O vínculo registrado em `projectmemberships` permitirá controlar a participação do usuário em cada projeto.

Um usuário poderá ter funções diferentes em projetos distintos.

O backend deverá verificar se o usuário possui acesso ao projeto e se a operação solicitada é permitida para sua função.

---

## Isolamento dos Dados

O Arqio será uma plataforma multiempresa. Isso significa que diferentes empresas utilizarão o mesmo sistema, mantendo seus dados separados.

### Regras

- Cada projeto deverá estar associado a uma empresa.
- Consultas a recursos empresariais deverão verificar o vínculo do usuário com a empresa correspondente.
- O acesso aos documentos deverá respeitar as permissões do projeto.
- Identificadores enviados pelo frontend não deverão ser considerados prova de autorização.
- O backend deverá verificar a relação entre usuário, empresa e recurso antes de permitir uma operação.
- Respostas da API não deverão incluir informações pertencentes a outras empresas sem autorização.

O isolamento deverá ser implementado no backend e aplicado a todas as operações relevantes.

---

## Proteção das Rotas

As rotas da API serão classificadas conforme a necessidade de autenticação.

### Rotas públicas

Poderão ser acessadas sem uma sessão autenticada, conforme a finalidade da funcionalidade.

Exemplos:

- Cadastro de usuário;
- Login;
- Solicitação de recuperação de senha.

### Rotas protegidas

Exigirão autenticação válida e, quando necessário, autorização específica.

Exemplos:

- Consultar os dados do usuário;
- Criar e consultar projetos;
- Gerenciar participantes;
- Consultar documentos;
- Acessar o histórico de conversas com o Airo;
- Gerenciar configurações da empresa.

A classificação definitiva será aplicada durante a implementação das rotas.

---

## Validação dos Dados

Todos os dados recebidos pela API deverão ser validados no backend.

A validação deverá verificar, conforme a operação:

- Presença dos campos obrigatórios;
- Formato dos dados;
- Limites de tamanho;
- Valores permitidos;
- Existência dos recursos referenciados;
- Permissões para executar a operação.

A validação realizada no frontend terá finalidade de melhorar a experiência do usuário, mas não substituirá a validação do backend.

---

## Recuperação e Alteração de Senha

O sistema deverá permitir que o usuário solicite a recuperação de sua senha.

O fluxo deverá utilizar um mecanismo seguro de redefinição, com token temporário, uso limitado e prazo de validade.

### Regras

- O token de recuperação não deverá ser reutilizável.
- O token deverá expirar.
- O sistema não deverá revelar desnecessariamente se um e-mail possui cadastro.
- A nova senha deverá ser armazenada como hash.
- Após a redefinição, sessões existentes deverão ser tratadas conforme a política de segurança adotada.

O envio de e-mails e a implementação completa desse fluxo serão definidos durante o desenvolvimento da funcionalidade.

---

## Tratamento de Falhas de Autenticação

A API deverá tratar adequadamente situações como:

- Credenciais inválidas;
- Token ausente em uma rota protegida;
- Token expirado ou inválido;
- Usuário sem permissão;
- Recurso inexistente;
- Tentativas excessivas de login.

Os códigos HTTP deverão seguir a convenção definida no documento `3.2-fluxo-da-aplicacao.md`.

A API deverá evitar mensagens que revelem informações sensíveis ou detalhes internos da implementação.

---

## Boas Práticas de Segurança

- Utilizar HTTPS em produção.
- Armazenar segredos em variáveis de ambiente.
- Não versionar arquivos que contenham credenciais ou segredos.
- Validar todas as entradas recebidas pela API.
- Aplicar controle de acesso no backend.
- Limitar tentativas de autenticação quando apropriado.
- Evitar exposição de informações sensíveis em logs.
- Manter as dependências utilizadas atualizadas.
- Configurar CORS para permitir somente as origens necessárias em produção.
- Tratar erros sem revelar detalhes internos.
- Proteger arquivos privados contra acessos não autorizados.

---

## Responsabilidades

### Frontend

- Coletar as credenciais do usuário.
- Enviar solicitações de autenticação.
- Apresentar mensagens de erro apropriadas.
- Manter a interface de acordo com o estado da sessão.
- Não tratar a ocultação de elementos da interface como mecanismo de segurança.

### Backend

- Verificar credenciais.
- Gerar e validar tokens.
- Validar os dados recebidos.
- Verificar permissões.
- Garantir o isolamento dos dados.
- Proteger operações e recursos privados.

### Banco de Dados

- Armazenar os dados necessários à autenticação e às permissões.
- Armazenar hashes de senhas, nunca senhas em texto puro.
- Preservar os relacionamentos entre usuários, empresas e projetos.

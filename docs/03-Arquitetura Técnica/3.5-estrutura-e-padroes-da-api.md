# 3.5 Estrutura e Padrões da API

## Objetivo

Este documento define os padrões de organização, nomenclatura e comunicação da API do Arqio.

A API será responsável por conectar o frontend ao backend, permitindo que as funcionalidades da plataforma sejam acessadas de forma organizada, consistente e segura.

---

## Tecnologia

A API será desenvolvida utilizando:

- Node.js para executar o backend;
- Express para definir rotas e processar solicitações HTTP;
- TypeScript para adicionar tipagem ao código;
- MongoDB e Mongoose para armazenar e consultar os dados.

A comunicação entre frontend e backend utilizará HTTP durante o desenvolvimento local e HTTPS em produção.

Os dados estruturados serão enviados e recebidos preferencialmente no formato JSON.

---

## Endereço Base

A API utilizará um endereço base configurado por ambiente.

Exemplos durante o desenvolvimento:

- Frontend: `http://localhost:5173`
- Backend: `http://localhost:3000`
- Endereço base da API: `http://localhost:3000/api/v1`

Em produção, o endereço será definido conforme a infraestrutura de hospedagem escolhida.

O endereço base deverá ser configurado por variável de ambiente, evitando que URLs específicas de desenvolvimento sejam utilizadas indevidamente em produção.

---

## Versionamento

As rotas da API utilizarão versionamento por URL.

A versão inicial será:

`/api/v1`

Esse padrão permitirá introduzir mudanças incompatíveis futuramente sem alterar imediatamente os clientes que utilizem uma versão anterior.

Durante o MVP, será mantida apenas a versão necessária ao funcionamento da plataforma.

---

## Padrões de Nomenclatura

As rotas deverão utilizar nomes descritivos, consistentes e preferencialmente no plural para representar coleções de recursos.

Exemplos:

- `/users`
- `/companies`
- `/projects`
- `/documents`
- `/conversations`
- `/subscriptions`

Os caminhos deverão utilizar letras minúsculas e hífens quando houver mais de uma palavra.

As operações deverão ser representadas pelos métodos HTTP adequados, evitando criar rotas diferentes para ações que possam ser expressas de maneira clara por esses métodos.

---

## Métodos HTTP

| Método | Finalidade | Exemplo |
|---|---|---|
| `GET` | Consultar recursos | `GET /projects` |
| `POST` | Criar um recurso | `POST /projects` |
| `PUT` | Substituir um recurso | `PUT /projects/:projectId` |
| `PATCH` | Atualizar parte de um recurso | `PATCH /projects/:projectId` |
| `DELETE` | Excluir um recurso, quando permitido | `DELETE /projects/:projectId` |

A utilização de cada método deverá respeitar as regras de negócio e as permissões da funcionalidade correspondente.

---

## Organização dos Endpoints

Os endpoints serão agrupados de acordo com os recursos da aplicação.

### Autenticação

- `POST /api/v1/auth/register`: cadastrar uma conta;
- `POST /api/v1/auth/login`: autenticar um usuário;
- `POST /api/v1/auth/logout`: encerrar a sessão conforme a estratégia adotada;
- `POST /api/v1/auth/forgot-password`: solicitar recuperação de senha;
- `POST /api/v1/auth/reset-password`: redefinir a senha.

### Usuários

- `GET /api/v1/users/me`: consultar os dados do usuário autenticado;
- `PATCH /api/v1/users/me`: atualizar os dados permitidos do próprio usuário.

### Empresas

- `POST /api/v1/companies`: cadastrar uma empresa;
- `GET /api/v1/companies/:companyId`: consultar uma empresa autorizada;
- `PATCH /api/v1/companies/:companyId`: atualizar informações permitidas da empresa.

### Projetos

- `POST /api/v1/companies/:companyId/projects`: criar um projeto;
- `GET /api/v1/companies/:companyId/projects`: listar os projetos acessíveis;
- `GET /api/v1/projects/:projectId`: consultar um projeto;
- `PATCH /api/v1/projects/:projectId`: atualizar um projeto;
- `DELETE /api/v1/projects/:projectId`: remover ou arquivar um projeto, conforme as regras definidas.

### Participantes de Projetos

- `GET /api/v1/projects/:projectId/members`: listar participantes;
- `POST /api/v1/projects/:projectId/members`: adicionar um participante;
- `PATCH /api/v1/projects/:projectId/members/:membershipId`: atualizar o vínculo ou as permissões;
- `DELETE /api/v1/projects/:projectId/members/:membershipId`: remover um participante.

### Documentos

- `GET /api/v1/projects/:projectId/documents`: listar documentos;
- `POST /api/v1/projects/:projectId/documents`: registrar um documento;
- `GET /api/v1/documents/:documentId`: consultar os metadados de um documento;
- `PATCH /api/v1/documents/:documentId`: atualizar informações permitidas.

O envio, o download e o versionamento de arquivos deverão ser implementados com mecanismos adequados de armazenamento e controle de acesso.

### Conversas com o Airo

- `GET /api/v1/projects/:projectId/conversations`: listar conversas acessíveis;
- `POST /api/v1/projects/:projectId/conversations`: criar uma conversa;
- `GET /api/v1/conversations/:conversationId`: consultar uma conversa;
- `POST /api/v1/conversations/:conversationId/messages`: enviar uma mensagem.

A integração com o serviço de inteligência artificial será implementada conforme a definição técnica dessa funcionalidade.

### Assinaturas

- `GET /api/v1/companies/:companyId/subscription`: consultar a assinatura da empresa.

A criação e a atualização de assinaturas deverão respeitar as regras comerciais e a integração de pagamentos que vier a ser adotada.

---

## Parâmetros das Solicitações

A API poderá receber informações por diferentes meios, conforme a finalidade da operação.

- **Parâmetros de rota:** identificam um recurso, como `projectId`.
- **Parâmetros de consulta:** permitem filtros, paginação e ordenação.
- **Corpo da solicitação:** transporta os dados de criação ou atualização.
- **Cabeçalhos HTTP:** transportam informações como o tipo de conteúdo e os dados de autenticação.

Os dados recebidos deverão ser validados no backend antes de serem utilizados.

---

## Padrão de Respostas

As respostas deverão seguir um padrão consistente para facilitar o tratamento no frontend.

### Resposta de sucesso

Exemplo ilustrativo:

```json
{
  "data": {
    "id": "identificador-do-projeto",
    "name": "Residência Modelo"
  }
}
```

### Resposta de erro

Exemplo ilustrativo:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Verifique os dados enviados."
  }
}
```

Os exemplos são ilustrativos. A estrutura definitiva será aplicada de forma consistente durante a implementação.

As respostas não deverão incluir senhas, tokens secretos ou outros dados internos desnecessários.

---

## Códigos HTTP

A API deverá utilizar códigos HTTP de acordo com o resultado da operação.

| Código | Utilização |
|---|---|
| `200` | Operação concluída com sucesso |
| `201` | Recurso criado com sucesso |
| `204` | Operação concluída sem conteúdo de resposta |
| `400` | Solicitação inválida |
| `401` | Autenticação necessária ou inválida |
| `403` | Acesso não permitido |
| `404` | Recurso não encontrado |
| `409` | Conflito com o estado atual do recurso |
| `422` | Dados compreendidos, mas não aceitos pelas regras de validação, quando adotado |
| `500` | Erro interno inesperado |

A aplicação deverá manter consistência no uso desses códigos.

---

## Autenticação e Autorização

Os endpoints deverão ser classificados de acordo com a necessidade de autenticação.

Nas rotas protegidas, o backend deverá identificar o usuário autenticado e verificar suas permissões antes de permitir o acesso.

A presença de um identificador válido na URL não será suficiente para autorizar uma operação.

O acesso aos dados deverá respeitar os vínculos entre usuários, empresas e projetos, conforme definido no documento `3.4-autenticacao-e-seguranca.md`.

---

## Validação e Tratamento de Erros

A API deverá:

- Validar parâmetros, cabeçalhos e corpo das solicitações conforme necessário;
- Rejeitar dados inválidos;
- Tratar recursos inexistentes;
- Verificar permissões antes de executar operações protegidas;
- Utilizar um tratamento centralizado de erros;
- Retornar mensagens compreensíveis sem revelar detalhes internos;
- Registrar erros inesperados de forma apropriada.

O frontend deverá interpretar os códigos HTTP e apresentar mensagens adequadas ao usuário.

---

## Paginação e Filtros

As rotas de listagem deverão permitir paginação quando necessário, evitando retornar quantidades excessivas de registros em uma única solicitação.

Poderão ser utilizados parâmetros de consulta como:

- `page`: número da página;
- `limit`: quantidade de registros por página;
- `search`: termo de pesquisa, quando aplicável;
- `status`: filtro por situação, quando aplicável.

Os filtros disponíveis serão definidos conforme as necessidades de cada recurso.

---

## Segurança

A API deverá seguir as seguintes práticas:

- Utilizar HTTPS em produção;
- Validar os dados recebidos;
- Aplicar autenticação e autorização no backend;
- Restringir o CORS às origens necessárias;
- Proteger operações contra acessos indevidos;
- Evitar exposição de informações sensíveis;
- Aplicar limites de requisições quando necessário;
- Manter dependências atualizadas;
- Armazenar segredos em variáveis de ambiente;
- Garantir o isolamento dos dados entre empresas.

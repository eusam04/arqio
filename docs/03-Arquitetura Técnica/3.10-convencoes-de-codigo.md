# 3.10 Convenções de Código e Organização do Desenvolvimento

## Objetivo

Este documento define as convenções que deverão ser seguidas durante o desenvolvimento do Arqio.

O objetivo é manter o código organizado, legível e consistente, facilitando a compreensão, a manutenção e a evolução da aplicação.

---

## Linguagens e Tecnologias

O desenvolvimento do Arqio utilizará:

- TypeScript para o frontend e o backend;
- React para a construção da interface;
- Vite para o desenvolvimento e a compilação do frontend;
- Node.js para executar o backend;
- Express para estruturar a API;
- MongoDB para armazenar os dados;
- Mongoose para modelar e consultar os dados;
- Git e GitHub para controle de versão.

As tecnologias deverão ser utilizadas de acordo com as responsabilidades definidas na arquitetura técnica.

---

## Nomenclatura de Arquivos e Pastas

Os nomes de arquivos e pastas deverão seguir um padrão consistente.

### Arquivos

Os nomes deverão indicar claramente a responsabilidade do arquivo.

Exemplos:

- `auth.controller.ts`
- `auth.service.ts`
- `user.model.ts`
- `project.routes.ts`
- `auth.middleware.ts`

No frontend, os componentes React poderão utilizar nomes em PascalCase.

Exemplos:

- `ProjectCard.tsx`
- `LoginForm.tsx`
- `MainLayout.tsx`

### Pastas

As pastas deverão possuir nomes claros e relacionados à responsabilidade dos arquivos armazenados.

Exemplos:

- `controllers`
- `services`
- `models`
- `routes`
- `middlewares`
- `components`
- `pages`

A nomenclatura deverá ser consistente dentro de cada parte da aplicação.

---

## Nomenclatura no Código

O código deverá seguir convenções de nomenclatura que facilitem a leitura.

### Variáveis e funções

Variáveis e funções utilizarão `camelCase`.

Exemplos:

- `userName`
- `companyId`
- `findProjectById()`
- `validateUserPermissions()`

### Classes e tipos

Classes, interfaces e tipos utilizarão `PascalCase`.

Exemplos:

- `ProjectService`
- `User`
- `CreateProjectInput`

### Constantes

Constantes que representem valores fixos e globais poderão utilizar `UPPER_SNAKE_CASE`.

Exemplos:

- `DEFAULT_PAGE_SIZE`
- `MAX_FILE_SIZE`

A convenção deverá ser aplicada com bom senso, evitando padrões diferentes para a mesma finalidade.

---

## Organização das Responsabilidades

Cada arquivo deverá possuir uma responsabilidade principal.

O código deverá respeitar a separação de camadas definida na arquitetura técnica.

### Controllers

Responsáveis por receber solicitações HTTP, acionar os services e retornar respostas.

### Services

Responsáveis por executar as regras de negócio.

### Models

Responsáveis por definir os schemas e a estrutura dos dados armazenados no MongoDB por meio do Mongoose.

### Routes

Responsáveis por definir os endpoints da API e associá-los aos controllers e middlewares.

### Middlewares

Responsáveis por executar verificações intermediárias, como autenticação e controles iniciais de acesso.

### Repositories

Quando utilizados, serão responsáveis por organizar as operações de acesso ao banco de dados.

A separação deverá ser proporcional à complexidade da funcionalidade, evitando criar camadas sem necessidade.

---

## Uso do TypeScript

O TypeScript deverá ser utilizado para tornar os tipos de dados explícitos e ajudar a identificar erros durante o desenvolvimento.

As seguintes práticas deverão ser priorizadas:

- Definir tipos para os dados relevantes;
- Evitar o uso desnecessário de `any`;
- Utilizar interfaces e tipos quando contribuírem para a clareza;
- Validar dados recebidos de fontes externas;
- Evitar duplicar definições de tipos sem necessidade;
- Manter as configurações de TypeScript consistentes.

A tipagem estática não substitui a validação de dados recebidos por formulários, requisições HTTP ou serviços externos.

---

## Tratamento de Erros

Os erros deverão ser tratados de forma consistente.

As funções deverão permitir identificar falhas relevantes e encaminhá-las para o tratamento apropriado.

No backend, os erros das solicitações HTTP deverão ser tratados de maneira centralizada sempre que possível.

As respostas enviadas ao frontend deverão utilizar códigos HTTP adequados e mensagens compreensíveis.

Detalhes internos, credenciais e informações sensíveis não deverão ser expostos.

---

## Comentários e Documentação

Os comentários deverão explicar decisões importantes ou comportamentos que não sejam evidentes pela leitura do código.

O código deverá priorizar nomes claros e estruturas compreensíveis, reduzindo a necessidade de comentários redundantes.

Decisões arquiteturais relevantes deverão ser registradas na documentação do projeto.

A documentação deverá ser atualizada quando uma mudança alterar significativamente o comportamento ou a organização da aplicação.

---

## Formatação e Consistência

O projeto deverá adotar regras consistentes de formatação e qualidade do código.

Ferramentas de formatação e análise estática poderão ser configuradas quando a estrutura inicial estiver preparada.

As regras deverão priorizar:

- Indentação consistente;
- Organização dos imports;
- Ausência de variáveis não utilizadas;
- Identificação de problemas comuns;
- Padronização do estilo do código.

As ferramentas definitivas serão escolhidas durante a configuração do projeto.

---

## Controle de Versão

O Git será utilizado para registrar as alterações realizadas no código e na documentação.

Os commits deverão:

- Representar alterações relacionadas entre si;
- Utilizar mensagens claras e descritivas;
- Evitar incluir arquivos desnecessários;
- Permitir identificar as etapas do desenvolvimento.

Quando uma etapa funcional ou documental importante for concluída, deverá ser avaliado se é um bom momento para realizar um commit.

O arquivo `.gitignore` deverá impedir o versionamento de dependências instaladas, arquivos de ambiente privados e outros arquivos que não devam integrar o repositório.

---

## Processo de Desenvolvimento

O desenvolvimento de cada funcionalidade deverá seguir um fluxo organizado:

1. Consultar os requisitos documentados.
2. Identificar as partes da aplicação envolvidas.
3. Implementar a funcionalidade.
4. Verificar o funcionamento.
5. Corrigir erros encontrados.
6. Atualizar a documentação, quando necessário.
7. Registrar as alterações no Git.

O desenvolvimento deverá avançar por etapas, priorizando as funcionalidades essenciais do MVP.

---

## Princípios Gerais

O código do Arqio deverá priorizar:

- Clareza;
- Consistência;
- Separação de responsabilidades;
- Segurança;
- Facilidade de manutenção;
- Reutilização quando apropriada;
- Simplicidade;
- Testabilidade.

A arquitetura deverá apoiar o desenvolvimento do produto sem introduzir complexidade desnecessária.
